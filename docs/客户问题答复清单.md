# 客户问题答复清单（第二种输出形态）

## 这是什么

原来的产出是「一个客户 + 一段时间 → 一篇 50~200 字的叙述式总结」。
新增的产出是「一个客户 + 一段时间 → 一张表格：客户提了哪些问题、我们怎么答复和处理的」。

两者可以一次跑完，写进**同一个 Excel 的两张 sheet**：

| sheet | 形态 | 一行代表 |
|---|---|---|
| `客户沟通总结` | 三列叙述（原有，未改动） | 一个客户 + 一个时间范围 |
| `客户问题答复清单` | 八列表格 | 一个问题和它的答复 |

## 表格列

| 列 | 说明 |
|---|---|
| 客户名称 | 聊天对象名 |
| 类型 | `提问` / `需求` / `报错` / `投诉` / `我方待办` |
| 提问时间 | 客户提出该问题的时间（`MM-DD HH:MM`） |
| 客户问题 | 客户问题的原话口径（清洗噪音后截断到 80 字） |
| 我方答复/处理 | 我方回复的原话口径（截断到 150 字）；未答复则为空 |
| 答复时间 | 我方回复的时间；未答复为 `—` |
| 状态 | `已答复` / `未答复（待跟进）` / `已承诺（待跟进）` |
| 原始记录 | 双方完整原话，用于核对抽取有没有改意思 |

关于**类型**里的 `我方待办`：这是刻意加进来的一类。客户没提问、但我们自己认领了要做的事
（"我拉一份字段映射表给你们确认"）也算一条，只是「客户问题」列显示 `—`。
好处是一张表既能看客户问过什么，也能看我们承诺了什么；不想要就按这一列筛掉。
状态列会标色：未答复标红、我方待办标橙，扫一眼就知道哪些没闭环。

## 判定范围

按"最宽"的口径收：疑问句、需求（希望/麻烦/帮我）、报错、投诉，外加我方主动承诺的待办。
同时用否定过滤排除假问题，例如「采购流没问题」不会被当成报错。

一句话可以同时命中多类时按优先级取一个标签：报错 > 投诉 > 需求 > 提问。
同一条消息里识别出的多个问题会合并成一行（客户一口气说的是同一件事，
拆成多行会出现"两个问题各配了一遍同样答复"的重复感）。

## 实现要点

代码在 `core/qa_extract.py`（离线规则引擎）与 `core/qa_ai.py`（AI 引擎）。
`engine` 配置决定用哪条：`auto`/`ai` 先试 AI，失败自动降级到离线并**明确告诉你降级原因**
（不悄悄换掉）；`offline` 完全不碰网络。

### AI 引擎：让模型引用消息序号，而不是自己写时间

聊天记录渲染成 `#序号 MM-DD HH:MM 发送人：内容`，模型只回答「问题序号」「答复序号」，
时间、原始记录一律用序号回填真实消息。这样做的好处：

- 模型**没有机会编造时间戳**，也不会因为 `MM-DD` 格式写歪而整条丢失
- 序号无效的条目直接丢掉，不会产生"没有时间、没有原话"的脏行
- 「原始记录」列必然是真实原话——这一列存在的意义就是能核对原话

模型的增值在于把口语归纳成规范表述，并且**综合整段对话给出实质性答复**，
而不是只抄我方第一条回复。实测同一段对话：

| | 离线 | AI |
|---|---|---|
| 客户问 | 您能帮我看一下这个同事为什么不能订酒店了他已经提交差旅申请了并且已经通过 | 同事已提交并通过差旅申请，但无法预订酒店，询问原因。 |
| 我方答 | 好，稍等我我看一下申请单 | 查到该同事的申请单中只有用餐项，没有酒店项，因此无法预订，建议变更申请后重新提交。 |

**分块**：`ChatBundle.transcript()` 超长时是「保开头+结尾、丢中间」，
这对问答清单是致命的——被丢掉的中间部分里的问题会无声消失。
所以 AI 引擎走 `iter_chunks()` 分块，保证每条消息都被模型看到过；
离线引擎更是逐条遍历、完全不经任何截断。

### 离线引擎：为什么不复用 summarizer 的判定正则

那套正则是为"写一段叙述总结"调的，宽容度换召回率。直接搬来判问答会出三类错，
都是实测踩到的：

| 借用的正则 | 踩到的错 |
|---|---|
| `_DEMAND_IMP` 里的 `请(帮\|协助\|处理)?` 允许裸「请」 | 「申请**单**」里的"请"被当成请求动词，整句判成需求 |
| 故障词里的「不能」 | 命中「能**不能**给个优惠」的子串，正常提问判成报错 |
| 愿望词里的裸「想」 | 命中「比我想的问题多」，一句评论判成需求 |

所以 `qa_extract.py` 另起了一套精度优先的线索，并把「能不能/能否/可不可以」
在扫故障词**之前**摘掉，避免子串误判。

**为什么不套用 `_clean_fact`**：它会把句子洗成客观短语碎片
（"我们这边 SSO 对接想本月底完成" → "SSO 对接想本月底完成"），那适合写进叙述总结；
但读表格的人想知道的是"客户原话问了什么"，洗碎了反而看不懂。完整原话进「原始记录」列。

**答复怎么配对**：从提问之后往前找第一条我方有效发言（跳过"嗯/收到"这类纯应答），
遇到下一个客户提问就停，避免把后面无关的我方消息错配给较早的问题；
超过 7 天（可配 `qa_answer_gap_days`）不再追。AI 引擎没有这个限制，
它可以跨多条消息综合出真正的处理结果。

### 清洗与载荷过滤（两条引擎共用）

真实微信记录里混着大量根本不是聊天内容的东西：XML/app 消息载荷、被截断的
CDATA、`<aeskey>`、以及藏在 `[类型xxx]` 后面的发送人标签。这些都经过
`summarizer._strip_message_noise()` 清洗，再用 `_looks_like_payload()` 兜一道。

踩过的坑：企微/OpenIM 桥接号形如 `10000000000000001@openim`，
发送人标签的字符集少了 `@` 就认不出来，随后 `@提及` 清理会把 `@openim` 吃掉，
只剩半截 `10000000000000001:` 永久留在正文里；被截断的消息还见过
`10000000000000001:57</aeskey>` 被当成"我方答复"混进表格。

#### 最严重的一个：企微图文消息的正文被整段丢掉

企微/OpenIM 桥接号（`local_type 244813135921`）发出来的消息长这样：

```xml
<msg><appmsg>
  <title><![CDATA[@王五 关于用餐，美团给到壬癸信息的资源是美团甄选的资源，
与美团C端资源会存在差异，如果没有没有，可以用支付宝企业码支付也行的；]]></title>
  <des /><type>57</type><showtype>0</showtype>
</appmsg></msg>
```

真正的对话文字在 `<title>` 里，`<type>57</type>` 只是个数字标记。
而原清洗顺序是「先剥 XML 标签、再删 CDATA」，`<[^>\n]*>` 是「`<` 到第一个 `>`」，
**会把 CDATA 正文连同标签一起吃掉**，只剩 `<type>57</type>` 的裸 `57`。

后果不是"有噪声"，是**丢数据**：我方答复变成一句 `57`，AI 拿到这种垃圾无从下笔，
只好把状态词写进答复栏，于是表格里出现 10 行「状态=已答复、答复正文=『已答复。』」——
一条真答过的问题看起来闭环了，实际零信息量。"看起来答复了"比"显示未答复"更危险。

修法是在任何 XML 剥离**之前**先把 `title`/`des` 正文捞出来（`_extract_cdata_body`）。
正文有两种写法，真实数据里都出现过，必须都认：

- `<title><![CDATA[…]]></title>`
- `<title>纯文本</title>`

`title` 优先于 `des`：聊天消息的 title 就是对方说的话，而卡片类消息的 des
只是"会议已开始，请尽快入会"这类系统提示，两者都取会把系统提示当成对话内容。

顺带修掉两个同源缺陷：

1. **中文发送人标签规则过宽**。原规则允许 32 个中文字符，于是
   `我看您发的链接是11:00的` 被当成 `我看您发的链接是11:` + 正文，
   剥完只剩 `00的`。现在限 8 字内、且冒号前后都不能紧邻数字
   （`会议时间:2026/07/28` 也因此不再被剥成 `2026/07/28`）。
2. **数字残渣被当成正文**。`<type>57</type><showtype>0</showtype>` 剥掉标签后
   拼成 `570`。现在加了通则：清洗后若没有任何文字（无中日韩字符、无字母），
   判为非语言内容丢弃——`好`/`收到`/`可以` 这类短回复不受影响。

修复效果（同一批真实数据，改动前后对比）：

| 指标 | 修复前 | 修复后 |
|---|---|---|
| 问答条目 | 107 条 | **114 条** |
| 未答复占比 | 22% | **16%** |
| 答复正文是状态词（「已答复。」） | 10 行 | **0 行** |
| 答复正文是数字残渣 | 有 | **0 行** |
| 状态=已答复但答复为空 | 0 行 | 0 行 |

具体例子——「租车标准通常情况下是多少」，修复前答复是 `已答复。`，
修复后是原话「这个就是租车的管控的所有维度，就这些车型」。

## 群聊必读：`self_names`

群聊里"我方"往往不止账号本人。同事用自己的号、或通过企微/OpenIM 桥接号
（形如 `10000000000000001@openim`）发言时，默认判定会把它当成"对方"发言，
于是答复大面积变成「未答复（待跟进）」。

**这不是抽取逻辑的问题，而是"我方"识别的问题。** 用 `--self-names` 补上即可：

```bash
python cli.py run --source wx4 --contacts "某某客户交付群" --preset 30d \
  --self-names "李四,张三,王五" --out 台账.xlsx
```

支持部分匹配：填「张三」能匹配到备注「张三 交付」。同一同事的多个账号
（个人号 + openim 桥接号）都会被算作我方。GUI 里对应「我方成员」输入框。

**不知道同事的号叫什么？** 让程序先猜、你来拍板：

```bash
python cli.py suggest-self --source wx4 --contacts "某某客户交付群" --preset 30d
```

它按行为证据排序并**逐条给出理由**：是不是企微桥接号、多少次紧跟在客户问句之后发言、
多少次用我方口吻主动认领。实测在真实交付群里，第一候选就是同事（两个号都列了出来），
客户方成员也能靠备注里的公司名识别出来。

只给候选、不自动改配置——判定"谁是同事"是业务问题，猜错会把客户的话当成我方答复，
比漏掉更难发现。

实测影响（求知望里交付运营群，近 60 天 687 条消息）：

| | 我方识别条数 | 抽取行数 | 其中未答复 |
|---|---|---|---|
| 不填 `self_names` | 121 | 127 | 95 |
| 填 `self_names` | 350 | 102 | 明显下降 |

填了之后答复才真正对得上。**不填的话，群聊的问答清单基本不可用。**

### 名称库：把同事名字存起来（`self_name_library`）

每次都要重输同一批同事名字很烦，所以加了一个持久的**名称库**。

关键设计是**库与选用分开**：

| 键 | 含义 | 谁在改 |
|---|---|---|
| `self_name_library` | 你认过的全部我方人员，长期存着 | 手动添加、Excel 导入、"确定"时把勾选的人存进来、显式删除 |
| `self_names` | **这一次**跑要把哪些人算作我方 | 勾选 |

如果两者合一，"这次先不算某同事"就变成"把他从库里删掉"，下次得重新导入——
所以取消勾选永远只是"这次不用"，要真删得点「从名称库删除」。
反过来，「确定」时会把本次勾选的人存进库（勾选等于你认过他是同事），
这样用着用着库就自己长全了。

Excel 导入是这里最容易出错的地方：真实员工花名册里有序号、部门、手机号、表头，
随便挑一列都会把 `研发部` 当成同事存进去。而名称库在 `wx4_live` 里是**按子串匹配**
判我方身份的，库里混进一个泛词就可能误伤真实客户发言。所以：

- **导入走严格过滤**（`clean_names`）：表头词、纯数字/日期/手机号、邮箱、部门与
  组织名一律剔掉；姓名列还得由用户在对话框里确认（程序会猜，表头含"姓名/成员/人员/name"
  的列优先，否则取名字最多的那列）。
- **手动输入不过滤，只提示**：你明确敲进来的名字应当尊重，静默丢弃会让人以为
  "加了但没生效"；但看起来不像人名时会在状态行/命令行提示核对。
- 过滤规则里有个刻意的松紧：单字后缀的组织词（部/科/组/室/处）要求整串至少 3 字，
  这样「研发部」被剔掉而「张科」这种真名能留下。名称库漏一个真名的后果是
  "同事的答复没算成我方"，比多几条噪声更难发现，所以偏向保留。

命令行也能存取，便于脚本化：

```bash
python cli.py config --show
python cli.py config --add-library "张三,李四"
python cli.py config --remove-library "李四"
python cli.py config --export-template "D:/同事名单.xlsx"   # 同界面的「导出 Excel 模版」
python cli.py config --import-library "D:/同事名单.xlsx" [--sheet 名单 --column 3]
python cli.py config --self-names "张三,李四"
```

命令行的导入与界面**语义一致：以文件为准**——文件里没有的人会从库里移除。
会删人时命令行默认拒绝执行并先把增删名单打出来，确认无误再加 `--force`，
等价于界面上那个确认框。

`suggest-self` 把「名称库 + 本次选用」都当作已知成员，不再重复推荐。

GUI 里的「导出 Excel 模版」给的是**带当前名称库的模版**：必填的「姓名」列表头
标红，说明写在单元格批注里（不占数据行）；库里的人已经填在「姓名」列，加人/删行后
用「导入 Excel…」导回，一次更新就完成了。
模版刻意**不写示例数据**：用户会直接填在示例下面，示例名字就被一起导进名称库了。

导入对话框里的「导入后同时勾选为本次使用」默认勾上，是给"这批就是本项目的人"
准备的。导入整个部门/公司的大名单时要取消它：`self_names` 一次性膨胀到几十人后，
`wx4_live` 的子串匹配会把更多人算成我方，客户的发言就可能被当成我们的答复，
问答清单会内容错配——这种错误比"漏了几条"难发现得多。

**一个容易踩的识别陷阱**：真实模板的表头常写成「姓名（必填）」「姓名*」，
而 `_HEADER_WORD` 要求整串等于或以「姓名」结尾，这类写法匹配不上——
结果**表头本身会被当成一个真人名存进名称库**。名称库又是按子串匹配判我方
身份的，混进去就可能误伤客户发言。所以 `clean_names` 比对前会先剥掉尾部
装饰（`undecorate_header`）：括号标注和星号去掉后再比，`姓名（必填）` 就能
正确识别为表头，而「李四（销售）」这种真名不受影响（剥完是「李四」，不匹配表头词）。

## 已验证 / 未验证

**已验证**（2026-09-11）：

- 抽取与导出在 demo 数据上逐条核对通过（21 行，分类与配对均正确）。
- 自动化测试 94 项全通过，覆盖两条引擎、名称库、导出隔离与模版
  （`test_qa_extract.py` 24 项、`test_qa_ai.py` 27 项、
  `test_self_discover.py` 9 项、`test_name_library.py` 34 项）。
- Excel 两张表的追加/覆盖互不干扰，有断言测试覆盖：
  两张表各自独立追加；`overwrite` 只重建目标表、不动另一张（**修前会删掉整张表**）；
  陌生工作簿原样不动（另存 `_2.xlsx`）；先跑"仅问答"再补"总结"会落进同一工作簿。
- AI 引擎降级路径被真实网络故障验证过：MaaS 端点 SSL `UNEXPECTED_EOF` 或
  `Read timed out` 时自动降级到离线，并在输出里明确打印降级原因与原始报错。
- 真实微信数据（Windows wx4 直读）：求知望里交付运营群、直客通结算服务群、
  馮玲（1 对 1）三个会话。AI 引擎在同一份数据上把口语问句归纳成规范表述，
  并综合出实质答复（见上文对比表）。
- 输出一致性校验：`已答复` 必有答复、`未答复` 必无答复、`我方待办` 问题列占位
  且答复时间留空、答复时间只在实际配上答复时填写。AI 输出 0 处不一致。
- 叙述式总结未受影响（demo 4/4 生成成功，AI 与离线引擎都跑过）。
- `suggest-self` 在真实群里正确识别出同事的两个账号，且不会把客户推上来。
- 图形界面（第③步）由三个脚本验证：界面逻辑冒烟、布局体检（含最小窗口压力测试）、
  真实数据端到端。详见下文「图形界面」一节。

**未验证 / 已知不足**：

- **AI 调用的稳定性依赖外部服务**：实测同一命令会偶发 SSL 失败（已降级）。
  没有做重试；一次网络抖动就会让整个会话退回离线质量。
- **离线引擎的答复取"我方第一条回复"**，可能只是一句"我在会上，晚点看"，
  而不是后来真正的解决方案。AI 引擎没有这个短板。
- AI 引擎的 `我方待办` 判定比离线保守（倾向并入答复），数量明显更少。
  这是 prompt 里刻意划的边界，但边界是否合适还需要你实际用一段时间再看。
- 少量噪声仍在：客户随口一句评论可能被收成一条。
- 群聊里未记录"是客户哪个人问的"（只有客户名称）。多联系人客户想区分到人需要加列。
- 界面上的「我方成员」扫描需要先勾选聊天对象；没勾选时只能手动输入名字（有提示引导）。
- 小屏（窗口高度 720px）下结果表格只剩约 46px，很挤。这是物理限制：输入区内容
  本身就占满，只能由可滚动的结果区承担。1366×768 这类屏幕建议最大化窗口。

### 界面部分实测到并修掉的问题

1. **⑤ 被挤出分配高度**：④ 新增单选后本区从约 200px 涨到 269px，把 ⑤ 顶到父容器之外
   75px，与执行行、结果区重叠。改法有两层——把长单选标签压成「一行选项 + 一行说明」
   （④ 回到 202px），并给布局第 0 行设 `minsize`，
   使窗口变矮时**缺口全部由可滚动的结果区承担，而不是让输入区溢出**。
   后者是结构性修复，以后再加控件也不会重演。
2. **后台线程更新界面会抛异常**：`_wx4_do_refresh` 在工作线程里直接调 `self.after(...)`，
   窗口销毁或主线程不在 `mainloop` 时会刷出 `RuntimeError: main thread is not in main loop`。
   统一收进 `App._ui()` 吞掉这两类异常。
3. 结果表格在最小窗口下只剩 19px（约半行），并掉③的日期为一行、收短说明后回到 46px。

### 界面部分的验证方式

界面没法靠单元测试覆盖，所以写了三个不依赖人工点击的检查脚本（`tests/` 下）：

| 脚本 | 作用 |
|---|---|
| `check_gui_smoke.py` | 假数据驱动界面逻辑：形态切换、列数、标色、两个编辑器、导出、清空，27 项断言 |
| `check_gui_layout.py` | 用 Tk 自报的几何数据体检布局，含**最小窗口压力测试**，能抓出"被挤出屏幕/压扁" |
| `check_gui_e2e_wx4.py` | 真实微信数据走「界面 → pipeline → Excel」全链路；需 `--contact` 指定对象（刻意不写默认值，公开仓库不写客户名） |

三个脚本都会**备份并还原真实 `config.json`**——界面里 `_sync_cfg()` 会写盘，
测试值不能留在用户配置里。

真实数据端到端结果（某交付群，本季度 725 条消息，离线引擎）：

导出的两张 sheet 行数与界面一致，且界面上修订过的内容确实写进了 Excel。
